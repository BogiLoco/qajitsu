# Project status

Roadmap stages 1–3 work end to end on the demo-shop: `qj fetch` → `qj plan` (analyst + planner, verified with a local Ollama model) → `qj approve` (SHA-256 freeze) → `qj run --env local` (author agent, static checks, sandboxed API runner, evidence, statuses computed by code, publish gates, matrix/CSV/XLSX/HTML). The self-test proves every seeded API bug ends FAILED and PASSED without its flag. `qj publish` posts the gated results to Jira Cloud or Data Center after a preview (stage 4). Stage 5: web and mixed cases run in a browser driven by the trusted parent (ADR-0004), with healing, timeline, transition graph, `qj logs`, `qj evidence`, `qj pull`. The self-test covers all seven seeded API and UI bugs. Stage 6: `qj run --build` starts the application from the run's worktree with Docker Compose or managed processes (labels, dynamic ports, 0600 env files, stubs, health checks, seed hook with the run marker), validates the configuration first (`qj env check`), and cleans up per policy; `qj runs`, `resume`, `clean`, `gc` with run locks. Stage 7: an independent auditor (a different model by default) reviews every PASSED against plan, results, evidence and screenshots and can only downgrade to NEEDS_REVIEW; an optional canary re-runs one PASSED case with an inverted expectation; every planned expectation needs its own `verify()`; `qj bench` measures detection, false FAILED, BLOCKED, plan acceptance, time and cost per model. Stage 8: mobile cases run on Android through Appium (UiAutomator2) with the device driven by the trusted parent; QAJitsu builds or downloads the app for the change SHA (GitHub Actions, GitLab CI, worktree build), starts and stops the emulator and Appium, records the screen, logcat and page source; iOS runs on a device farm or is BLOCKED with the reason. The self-test catches BUG-08 on a real emulator. Stage 9: `qj init` onboards other projects (git host, compose services, OpenAPI, test types), `qj doctor --online` checks secrets, Docker, mobile tooling, Jira and code hosts; runs export OpenTelemetry traces, logs and metrics; `qj metrics` feeds Prometheus with example alerts; the journal is a hash chain (`qj audit verify`, `journal-intact` gate, separate audit retention); `pnpm run docs` builds the TypeDoc site; CI runs on Linux and macOS. Stage 10: pipelines. `qj ci detect` (label, `/qa approve`/`/qa revise` comments from people with write access, manual and Jira triggers), `qj ci publish-plan` and `qj ci comment` (plan and results on the PR/MR and Jira, status check), approval with a named approver or reuse of an approved plan when the ticket is unchanged, `qj export` (report.html, junit.xml, evidence zip); a GitHub Action with an example workflow, a GitLab CI template, a Docker image and a Jenkinsfile. All ten roadmap stages were implemented as first scoped. Stages 2, 3, 6 and 7 are extended with projects and the knowledge base (REQ-PRJ, REQ-KNOW, implemented): several projects on one machine under `~/.qajitsu/projects/<slug>/` with `qj init`, `use`, `status`, `note`, `resume`, isolation enforced by the guard and an adversarial suite, `work reset`, `clean --project`, `projects remove|archive`, `runs --keep`, `projects export|import`, and a code index cache by `<repo>@<sha>`; a per-project knowledge base (`qj knowledge add|sync|remove|reset|reindex|list|search`; Markdown, text, HTML, DOCX, PDF, OpenAPI, Confluence spaces, resolved Jira bugs) on embedded LanceDB or a shared Chroma server, full or hybrid retrieval by size, secrets masked before indexing, and `search_docs` for the analyst and planner with documentation quotes checked verbatim by code; `qj bench --knowledge compare` measures what it adds; `qj promote` turns PASSED cases into a pull/merge request to the tests repository (REQ-PUB-08); search stays under 100 ms p95 at 1 million chunks. Later additions: failure hints for FAILED cases (product bug, test bug, environment, data) with code-checked citations; `qj bug` reports failures to Jira after a search for similar open bugs; manual steps answered by a person in the terminal or with `qj answer` (ADR-0008); message capture for e-mails, SMS gateways and webhooks (webhook.site); a browser and viewport matrix; locale runs with per-locale expectations; visual regression against approved baselines (`qj baseline accept`); test depth (`qj plan --depth`), a run estimate and a budget; `qj release` for release readiness over a fix version or sprint, where a ticket without a run is never ready; existing manual test cases imported from Xray, Zephyr Scale, TestRail or CSV/Excel as a cited, untrusted planner source; the application map around the change as a source of regression cases; `qj run --cases --headed --step` to watch a case live; progress lines in `qj run` and a live page with `qj watch`; `qj regression` runs the promoted packs again without models, hash-checked; failed web and mobile steps get screenshots with the failing elements and changed regions boxed in red; `qj doctor` lists the versions of every tool and of the application under test, and every run records the tool and model versions it used. `qj setup` installs the tools a project needs (browsers, Docker through Colima or Docker Engine, Temurin Java, the Android SDK with emulator and AVD, Appium and its drivers, Xcode through xcodes) at pinned versions into `~/.qajitsu/toolchain/`, checksum-verified, leaving the user's compatible tools and shell alone, with mirrors, proxy, company CA, offline bundles and `qj doctor --fix`. API, web and mobile cases run at the same time in lanes (or one by one with `--sequential`), on several browsers and several different phones or tablets at once, and each running case holds its own test accounts from a pool. Every one of them can only make a result stricter: a missing answer, message, browser, locale or baseline is BLOCKED or NEEDS_REVIEW, never PASSED. Exploratory sessions of the web app and of command-line tools (`qj explore`, live terminal view, claims checked against the recorded actions) feed the planner only with what a person accepted (`qj explore review`, REQ-PLAN-11). Plans can pass an approval flow of person and model steps (REQ-PLAN-10, ADR-0010): every decision is recorded with hashes, checked by `qj audit verify` and the `approval-intact` gate, posted to Jira as separate comments, and a plan no person approved is marked in every report. Every run keeps a complete audit trail (REQ-VER-16): every prompt, answer and tool call of every model, masked, with its hash in the journal; container image digests; `qj audit trail` lists every file with its SHA-256 and the gaps, `qj audit export` gives an auditor one zip with `SHA256SUMS`. A run with a complete trail gets a signed certificate (REQ-VER-15: in-toto statement in a DSSE envelope, Ed25519 key from the secret provider, RFC 6962-style Merkle root, key rotation) shown in `report.html` and the Jira comment; `qj verify-report` and the dependency-free `tools/verify-certificate.mjs` check it offline and name every changed file (REQ-VER-21). Generated specs pass a test code quality gate (REQ-VER-23: no constant or skippable assertions, no swallowed errors, no disabled cases, no whole-page checks), and a person can review them before they run (REQ-VER-24, `qj review-spec`). Each run reports its cost per verified ticket (by role, week and dated prices with cache rates), where its time goes and which stages ran over budget, plan quality and an agent scorecard, with `qj feedback` for false FAILED and escaped defects (REQ-LLM-11, REQ-NFR-11, REQ-PLAN-16, REQ-LLM-14); prompt caching and input limits per call (REQ-LLM-12); a readiness gate with risk level before the first plan (REQ-PLAN-13); `qj reproduce` runs a certified run again without agents (REQ-VER-20). QAJitsu works inside the team's Jira workflow (REQ-FLOW-02..05): statuses mapped per role and checked by `qj doctor`, the ticket moved by the computed result after publishing, plan approval by `/qj approve`, `revise` and `reject` comments from a Jira group with reminders (`qj workflow sync`), one active run per ticket and a daily limit. Tickets are picked up from the start status by polling or a signed webhook (`qj workflow poll|serve`, REQ-FLOW-01). Certificates get trusted RFC 3161 timestamps checked offline (REQ-VER-17), and certified runs can be kept in write-once storage on S3 Object Lock that cleanup respects (REQ-VER-19). Web cases test real pages beyond forms (REQ-EXEC-38..40, REQ-EXEC-56, REQ-EXEC-61, ADR-0013): uploads and downloads checked by content, iframes, pop-ups and tabs, hover, drag and drop, keys, infinite scrolling, Shadow DOM, canvas through a test hook or an element screenshot, browser dialogs, a planned clock, permissions and location, selectors narrowed by their context (REQ-EXEC-64), installable apps with their manifest and service worker and offline mode (REQ-EXEC-65), cookie sessions and account secrets typed by the runner into login forms, with traces masked (REQ-EXEC-67), Google Chrome and Microsoft Edge channels in the browser matrix with the exact browser version recorded per attempt (REQ-EXEC-66),, the WebSocket messages of the page (REQ-EXEC-47/AC3), and the recorded traffic read by code: failed steps list the requests that went wrong and the report shows which case reached which endpoint of the change (REQ-EVD-09/AC1+AC2), and staging behind HTTP authentication; the assertion lock also compares actions and control flow, so a healer cannot change what a test does.
