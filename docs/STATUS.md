# Project status

Roadmap stages 1–3 work end to end on the demo-shop: `qj fetch` → `qj plan` (analyst + planner, verified with a local Ollama model) → `qj approve` (SHA-256 freeze) → `qj run --env local` (author agent, static checks, sandboxed API runner, evidence, statuses computed by code, publish gates, matrix/CSV/XLSX/HTML). The self-test proves every seeded API bug ends FAILED and PASSED without its flag. `qj publish` posts the gated results to Jira Cloud or Data Center after a preview (stage 4). Stage 5: web and mixed cases run in a browser driven by the trusted parent (ADR-0004), with healing, timeline, transition graph, `qj logs`, `qj evidence`, `qj pull`. The self-test covers all seven seeded API and UI bugs. Stage 6: `qj run --build` starts the application from the run's worktree with Docker Compose or managed processes (labels, dynamic ports, 0600 env files, stubs, health checks, seed hook with the run marker), validates the configuration first (`qj env check`), and cleans up per policy; `qj runs`, `resume`, `clean`, `gc` with run locks. Stage 7: an independent auditor (a different model by default) reviews every PASSED against plan, results, evidence and screenshots and can only downgrade to NEEDS_REVIEW; an optional canary re-runs one PASSED case with an inverted expectation; every planned expectation needs its own `verify()`; `qj bench` measures detection, false FAILED, BLOCKED, plan acceptance, time and cost per model. Stage 8: mobile cases run on Android through Appium (UiAutomator2) with the device driven by the trusted parent; QAJitsu builds or downloads the app for the change SHA (GitHub Actions, GitLab CI, worktree build), starts and stops the emulator and Appium, records the screen, logcat and page source; iOS runs on a device farm or is BLOCKED with the reason. The self-test catches BUG-08 on a real emulator. Stage 9: `qj init` onboards other projects (git host, compose services, OpenAPI, test types), `qj doctor --online` checks secrets, Docker, mobile tooling, Jira and code hosts; runs export OpenTelemetry traces, logs and metrics; `qj metrics` feeds Prometheus with example alerts; the journal is a hash chain (`qj audit verify`, `journal-intact` gate, separate audit retention); `pnpm docs` builds the TypeDoc site; CI runs on Linux and macOS. Stage 10: pipelines. `qj ci detect` (label, `/qa approve`/`/qa revise` comments from people with write access, manual and Jira triggers), `qj ci publish-plan` and `qj ci comment` (plan and results on the PR/MR and Jira, status check), approval with a named approver or reuse of an approved plan when the ticket is unchanged, `qj export` (report.html, junit.xml, evidence zip); a GitHub Action with an example workflow, a GitLab CI template, a Docker image and a Jenkinsfile. All ten roadmap stages were implemented as first scoped. Stages 2, 3, 6 and 7 are extended with projects and the knowledge base (REQ-PRJ, REQ-KNOW, implemented): several projects on one machine under `~/.qajitsu/projects/<slug>/` with `qj init`, `use`, `status`, `note`, `resume`, isolation enforced by the guard and an adversarial suite, `work reset`, `clean --project`, `projects remove|archive`, `runs --keep`, `projects export|import`, and a code index cache by `<repo>@<sha>`; a per-project knowledge base (`qj knowledge add|sync|remove|reset|reindex|list|search`; Markdown, text, HTML, DOCX, PDF, OpenAPI, Confluence spaces, resolved Jira bugs) on embedded LanceDB or a shared Chroma server, full or hybrid retrieval by size, secrets masked before indexing, and `search_docs` for the analyst and planner with documentation quotes checked verbatim by code; `qj bench --knowledge compare` measures what it adds; `qj promote` turns PASSED cases into a pull/merge request to the tests repository (REQ-PUB-08); search stays under 100 ms p95 at 1 million chunks. Later additions: failure hints for FAILED cases (product bug, test bug, environment, data) with code-checked citations; `qj bug` reports failures to Jira after a search for similar open bugs; manual steps answered by a person in the terminal or with `qj answer` (ADR-0008); message capture for e-mails, SMS gateways and webhooks (webhook.site); a browser and viewport matrix; locale runs with per-locale expectations; visual regression against approved baselines (`qj baseline accept`); test depth (`qj plan --depth`), a run estimate and a budget; `qj release` for release readiness over a fix version or sprint, where a ticket without a run is never ready; existing manual test cases imported from Xray, Zephyr Scale, TestRail or CSV/Excel as a cited, untrusted planner source; the application map around the change as a source of regression cases; `qj run --cases --headed --step` to watch a case live; progress lines in `qj run` and a live page with `qj watch`; `qj regression` runs the promoted packs again without models, hash-checked; failed web and mobile steps get screenshots with the failing elements and changed regions boxed in red. Every one of them can only make a result stricter: a missing answer, message, browser, locale or baseline is BLOCKED or NEEDS_REVIEW, never PASSED.
